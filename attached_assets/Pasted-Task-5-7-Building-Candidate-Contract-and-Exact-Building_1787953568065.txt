2. BUILDING CANDIDATE TYPE
==================================================

Create:

backend/app/matching/candidates.py

Define:

@dataclass(frozen=True, slots=True)
class BuildingCandidate

Fields:

key: str

address_normalized: str

city: str | None

latitude: float | None

longitude: float | None

building_type: str | None

floors_total: int | None


Semantics:

key
    Framework-independent candidate identity.

    A future SQLAlchemy provider may use:
    str(building.id)

    The matcher itself must not know this is a database UUID.


address_normalized
    Canonical address representation supplied by the candidate provider.

    ExactBuildingMatcher will compare this with a normalized representation of
    the listing address.

==================================================

4. CANDIDATE PROVIDER CONTRACT
==================================================

In the same module define:

class BuildingCandidateProvider(ABC)

with one abstract method:

get_candidates(
    listing: NormalizedListing,
) -> list[BuildingCandidate]


Responsibilities:

The provider is responsible only for supplying plausible building candidates.

It is NOT responsible for deciding which candidate matches.

The matcher owns the matching decision.


Do NOT implement SQLAlchemy provider yet.

6. ADDRESS CANONICALIZATION FOR MVP
==================================================

For Task #5.7 implement only minimal deterministic address canonicalization.

Create a private helper inside exact_building.py, for example:

_normalize_address(value: str) -> str


The MVP normalization must perform ONLY:

1. strip leading/trailing whitespace;
2. convert to lowercase;
3. collapse repeated whitespace to one space.

Example:

"  Москва,  Улица Ленина, 1  "

becomes:

"москва, улица ленина, 1"


Do NOT:

- transliterate;
- expand abbreviations;
- replace "ул." with "улица";
- parse house number;
- remove punctuation;
- use regex-heavy Russian address parsing;
- use external address services;
- use fuzzy matching.

This is intentionally minimal.


==================================================
7. EXACT MATCHING RULE
==================================================

ExactBuildingMatcher must:

1. obtain candidates from candidate_provider;

2. normalize listing["address"] using the MVP helper;

3. compare it with normalized candidate.address_normalized using the same
   helper;

4. consider exact normalized address equality the primary rule.


Cases:


CASE A — no candidates

Return:

BuildingMatchResult(
    matched=False,
    candidate_key=None,
    confidence=0.0,
    reason="no_candidates",
)


CASE B — exactly one exact-address candidate

Return:

matched=True

candidate_key=<candidate.key>

confidence=1.0

reason="exact_address"


CASE C — multiple candidates share the same exact normalized address

Use additional deterministic fields only as tie-breakers.

Allowed tie-breakers:

- city;
- building_type;
- floors_total.

Do NOT use apartment floor, rooms, area, or price.


Tie-break logic must remain simple and explicit.

Preferred behavior:

For each exact-address candidate, compute one point for every non-null field
that exactly matches the corresponding listing value:

- city
- building_type
- floors_total vs listing.total_floors

Choose a candidate only if ONE candidate has a strictly higher score than all
others.

If exactly one candidate wins:

matched=True
candidate_key=<winner.key>
confidence=0.95
reason="exact_address_tiebreak"


If there is still a tie:

matched=False
candidate_key=None
confidence=0.0
reason="ambiguous_exact_address"


CASE D — candidates exist but no exact normalized address match

Return:

matched=False
candidate_key=None
confidence=0.0
reason="no_exact_address_match"


==================================================
8. IMPORTANT MATCHING RULES
==================================================

Do NOT use coordinates for matching yet.

Coordinates exist in the candidate contract for future Task(s), but #5.7 is
strictly exact-address matching.

Do NOT infer matches based on:

- nearby coordinates;
- same city only;
- same building type only;
- same floors_total only.

Exact normalized address equality is mandatory.
