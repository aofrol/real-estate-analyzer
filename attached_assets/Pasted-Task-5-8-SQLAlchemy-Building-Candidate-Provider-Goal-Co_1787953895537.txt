Task #5.8 — SQLAlchemy Building Candidate Provider

Goal:
Connect the framework-independent building matching layer to the existing
`buildings` table through a SQLAlchemy candidate provider.

This task must:

1. introduce one shared minimal address canonicalization helper;
2. implement SQLAlchemyBuildingCandidateProvider;
3. map ORM Building rows into framework-independent BuildingCandidate objects;
4. keep ExactBuildingMatcher unchanged in behavior;
5. perform candidate retrieval only — NOT the final matching decision.

Do NOT implement fuzzy matching.
Do NOT implement PostGIS distance matching.
Do NOT create buildings.
Do NOT modify database schema or migrations.

        ↓

        ↓

==================================================
5. PROVIDER RESPONSIBILITY
==================================================

The provider is responsible for:

- querying plausible Building rows;
- translating Building ORM rows into BuildingCandidate objects.

The provider is NOT responsible for:

- deciding whether a building matches;
- assigning confidence;
- creating BuildingMatchResult;
- fuzzy matching;
- geographic distance scoring;
- creating or updating buildings;
- transaction commits;
- normalization of apartment attributes.


==================================================
6. MVP CANDIDATE QUERY
==================================================

Implement:

get_candidates(
    self,
    listing: NormalizedListing,
) -> list[BuildingCandidate]


Use:

listing["address"]

as the required input.


First canonicalize it with:

canonicalize_address(...)


Then retrieve candidate buildings using the existing:

Building.address_normalized


For Task #5.8 use a deterministic equality prefilter.

The SQL query should conceptually be:

Building.address_normalized == canonicalized listing address


IMPORTANT:

The stored `Building.address_normalized` may not always be canonicalized by the
same helper historically.

For this MVP task, assume the field represents canonical address data.

Do NOT apply SQL LOWER(), regexp_replace(), fuzzy SQL operators, LIKE, ILIKE,
or PostGIS search yet.

We want a simple indexed equality path.


==================================================
7. OPTIONAL CITY FILTER
==================================================

If:

listing["city"] is not None

also apply exact equality:

Building.city == listing["city"]


If city is None:

do not add a city predicate.


Therefore:

address is mandatory candidate prefilter.

city is an optional narrowing predicate.


Do NOT reject candidates using:

- building_type;
- floors_total;
- coordinates.

Those belong to the matcher tie-break strategy already implemented.


==================================================
8. SQLALCHEMY QUERY STYLE
==================================================

Use SQLAlchemy 2.x style if that is the project's current convention.

Preferred shape:

stmt = select(Building).where(...)

rows = self._session.scalars(stmt).all()


But follow actual project conventions discovered during inspection.

Do not introduce legacy Query API if the project does not use it.

16. IMPORTANT ARCHITECTURAL NOTE
==================================================

There is a subtle distinction:

NormalizedListing.address
    = canonical source-level address string available after normalization

Building.address_normalized
    = persisted building identity address


For the current MVP we assume that both can be compared after applying the
shared minimal `canonicalize_address()` rule to the listing address.

Do NOT redesign NormalizedListing in this task.

Do NOT add address_normalized to NormalizedListing yet.
