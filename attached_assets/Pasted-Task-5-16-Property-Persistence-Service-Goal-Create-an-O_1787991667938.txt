Task #5.16 — Property Persistence Service

Goal:
Create an ORM-aware PropertyPersistenceService that applies an already-made
PropertyResolutionResult to the database.

This service must:

1. reuse an existing Property when resolution.status == "matched";
2. create exactly one Property when resolution.status == "create_required";
3. refuse to persist when resolution.status == "ambiguous";
4. never commit, rollback, close, or own the transaction;
5. perform no matching or resolution logic.

This task is the persistence boundary after PropertyResolutionService.


CURRENT FLOW

NormalizedListing
      +
building_key
      +
PropertyResolutionResult
      ↓
PropertyPersistenceService
      ↓
Property ORM instance

- manage transactions.

==================================================
5. BUILDING KEY VALIDATION
==================================================

Validate:

building_key must be:

- str;
- non-empty after strip;
- valid UUID.


Invalid value must raise ValueError containing:

building_key


Examples:

""
"   "
"not-a-uuid"


Do not query the session when building_key validation fails.


==================================================
6. BUILDING EXISTENCE
==================================================

Parse:

building_id = UUID(building_key)


Load:

building = self._session.get(Building, building_id)


If Building does not exist:

raise ValueError containing:

building_key


Example message:

raise ValueError(
    f"Building not found for building_key: {building_key}"
)


This check applies before creating a Property.


For matched resolution, inspect BuildingPersistenceService behavior and choose
the minimal consistent approach.

Preferred rule:

- validate building_key;
- ensure Building exists;
- then resolve/load Property.

Do not silently create Building here.


==================================================
7. MATCHED STATUS
==================================================

If:

resolution.status == "matched"


Then:

1. resolution.property_key must already be non-empty by its own invariant;
2. parse property_key as UUID;
3. invalid UUID raises ValueError containing:

property_key

4. load:

property_row = self._session.get(Property, property_id)

5. if missing:

raise ValueError containing:

property_key

6. verify:

property_row.building_id == building_id


If the matched Property belongs to a different Building:

raise ValueError containing both:

property_key
building_key


This is an important persistence safety guardrail.


Do NOT:

- mutate the Property;
- overwrite fields from listing;
- add Property;
- flush;
- commit.


Return the existing ORM Property unchanged.


==================================================
8. CREATE_REQUIRED STATUS
==================================================

If:

resolution.status == "create_required"


Create exactly one Property using canonical listing data.


Required mapping:

Property(
    building_id=building_id,
    floor=listing["floor"],
    rooms=listing["rooms"],
    area_total=listing["area_sqm"],
    is_studio=listing["is_studio"],
)


Inspect Property model for any additional required fields.

If any other Property fields are NOT NULL without defaults:

STOP and report instead of inventing values.


Do not populate fields that are not represented canonically unless required by
the ORM schema.


==================================================

==================================================

Inspect:

Property.area_kitchen


If nullable:

leave them as None/default.

Do NOT infer them from total area.

Do NOT invent data.


==================================================
10. CANONICAL STUDIO CONTRACT
==================================================

Persistence must accept the canonical representation established in Task #5.14:

Non-studio:

Do NOT convert:

0 -> None
None -> 0
0 -> 1
1 -> 0


Do NOT add studio-specific transformation logic.

Normalization already owns canonicalization.


==================================================
11. ADD AND FLUSH
==================================================

For create_required only:

self._session.add(property_row)
self._session.flush()


Then return:

property_row


Do NOT call:

commit()
rollback()
close()


Transaction ownership belongs to higher-level orchestration.


==================================================
12. AMBIGUOUS STATUS
==================================================

If:

resolution.status == "ambiguous"


Raise ValueError before any write operation.


Error must contain:

ambiguous


Example:

raise ValueError(
    "Cannot persist Property from ambiguous resolution"
)


CRITICAL:

For ambiguous resolution:

- no Property creation;
- no add;
- no flush;
- no commit;
- no mutation.


Prefer failing before any unnecessary database write.

It is acceptable to validate pure input values before the status branch, but
do not create or write anything.


==================================================
13. UNKNOWN STATUS
==================================================

PropertyResolutionResult already validates status.

Do not add speculative fallback logic.

Still fail closed if somehow unsupported state reaches persistence.


==================================================
14. MATCHED PROPERTY OWNERSHIP GUARD
==================================================

This is required.

Scenario:

building_key references Building A

resolution.property_key references Property belonging to Building B


Persistence must reject this.

Never return a Property from another Building even if the matcher/resolution
layer somehow supplied that key.


Expected:

ValueError


No writes.
