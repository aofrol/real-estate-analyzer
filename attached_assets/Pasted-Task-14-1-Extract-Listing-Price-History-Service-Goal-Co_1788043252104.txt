Task #14.1 — Extract Listing Price History Service

Goal:
Correct Task #14 architecture by extracting price-history persistence from
ListingPersistenceService into a dedicated ListingPriceHistoryService.

This is an architectural correction.

The existing behavior is functionally correct:
- history is created only when price changes;
- unchanged price creates no history;
- new Listing creates no history;
- transaction ownership stays with caller.

But ListingPersistenceService must NOT own ListingPriceHistory persistence.

The goal is to preserve behavior while restoring separation of responsibilities.

==================================================
2. REQUIRED ARCHITECTURE
==================================================

ListingPersistenceService owns:

- Listing hard identity;
- Listing creation/reuse;
- Property consistency;
- current marketplace state;
- current asking price;
- current asking price per sqm;
- URL;
- listed_at;
- duplicate_of_id preservation.

ListingPersistenceService must NOT own:

- ListingPriceHistory creation;
- price-history querying;
- price-history deduplication;
- historical timestamps.


ListingPriceHistoryService owns:

- deciding whether a price history record is required;
- creating ListingPriceHistory;
- adding/flushing history;
- no Listing identity decisions;
- no Listing mutable-state persistence;
- no commit/rollback/close.

==================================================
4. PRICE CHANGE CONTRACT
==================================================

Behavior:

previous_price_kopecks == new_price_kopecks
    → return None
    → no add
    → no flush


previous_price_kopecks != new_price_kopecks
    → create exactly one ListingPriceHistory row
    → associate it with listing.id
    → persist the NEW observed price unless existing schema/docs explicitly
      define another semantics
    → add exactly once
    → flush exactly once
    → return created history row


Do NOT create a history row for initial Listing creation.

Initial Listing price already represents the starting state.

==================================================
7. ORCHESTRATION BOUNDARY
==================================================

Do NOT make ListingPersistenceService call ListingPriceHistoryService.


That would preserve the same coupling indirectly.


Instead document the intended future orchestration:

previous_price = existing_listing.asking_price

ListingPersistenceService updates current Listing state

ListingPriceHistoryService.record_change(
    listing=listing_row,
    previous_price_kopecks=previous_price,
    new_price_kopecks=normalized["asking_price_kopecks"],
)


However, be careful:

The orchestration layer must capture previous_price BEFORE mutation.


Do not implement a broad orchestration layer in this correction task unless one
already exists and is explicitly in scope.


==================================================
8. IMPORTANT ORDERING CONTRACT
==================================================

Document explicitly:

For an existing Listing:

1. capture persisted previous asking price;
2. determine incoming canonical price;
3. persist/update Listing current state;
4. record price history if previous != incoming;
5. caller commits the enclosing transaction.


Both operations belong to one caller-owned transaction.


If history persistence fails:

the outer orchestration layer must be able to roll back the whole transaction.


Neither service commits.
