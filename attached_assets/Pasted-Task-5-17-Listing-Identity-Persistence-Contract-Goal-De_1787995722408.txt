==================================================
2. DO NOT ASSUME RAWLISTING AND LISTING HAVE THE SAME IDENTITY
==================================================

Treat these as distinct concepts:

RawListing:
    one persisted source payload / ingestion artifact

Listing:
    one normalized marketplace advertisement identity

Property:
    one physical real-estate object


Do not collapse them into one concept.


==================================================
3. DEFINE THREE DIFFERENT IDENTITIES
==================================================

The contract must explicitly distinguish:

A. PHYSICAL PROPERTY IDENTITY

Represents:
    the real-world apartment/unit.

Owned by:
    Property.


B. SOURCE LISTING IDENTITY

Represents:
    one advertisement as identified by one marketplace/source.

Conceptual key:

    source_id + external_id


C. CROSS-SOURCE OFFER IDENTITY

Represents:
    the hypothesis that two different source listings describe the same
    commercial offer.

This must NOT be treated as hard identity.

Cross-source equivalence is probabilistic / heuristic and belongs to a later
deduplication layer.


==================================================
4. REQUIRED PRIMARY CONTRACT DECISION
==================================================

Unless inspection proves the schema makes this impossible, adopt this rule:

Within one Source:

    (source_id, external_id)

is the hard identity of a Listing.


Meaning:

Same source_id + same external_id:
    same Listing identity.

Different source_id:
    different Listing identity even if external_id strings are equal.

Different external_id:
    different Listing identity even when Property is the same.


Do NOT use:

property_id

as the hard identity of Listing.


One Property may have multiple Listings.


==================================================
5. SAME-SOURCE REOBSERVATION RULE
==================================================

Define expected behavior when the same:

source_id + external_id

is collected again.


Preferred contract:

If Listing already exists for:

    source_id + external_id

then:

- reuse the existing Listing row;
- do not create a second Listing solely because it was observed again;
- update mutable marketplace state where appropriate;
- record price change through ListingPriceHistory in a later dedicated service;
- preserve the stable Listing id.


This task must define the rule but MUST NOT implement it.


==================================================
6. PROPERTY RELATIONSHIP
==================================================

Define:

Listing.property_id

as:

the physical Property currently associated with the advertisement.


Expected invariant:

A Listing points to exactly one Property.


However:

One Property may have:

- one Listing;
- multiple Listings on one source;
- Listings across multiple sources.


Therefore:

property_id is NOT unique.


Do not propose a unique constraint on property_id.


==================================================
7. SOURCE RELATIONSHIP
==================================================

Inspect Listing.source_id.


Define source_id as:

the marketplace/source that owns the external listing identity.


Expected hard identity:

source_id + external_id


Do not use source_url as identity.


URLs may change.


==================================================
8. EXTERNAL ID CONTRACT
==================================================

Define external_id as:

the source-native stable advertisement identifier.


Rules:

- non-empty;
- meaningful only within Source namespace;
- opaque application value;
- do not parse business meaning from it;
- do not assume numeric;
- do not assume globally unique.


Do not canonicalize different source IDs into one ID.


==================================================
9. DUPLICATE_OF_ID SEMANTICS
==================================================

Inspect current self-FK.

Define duplicate_of_id explicitly.


Preferred contract:

duplicate_of_id means:

    "this Listing has been classified as a duplicate of another Listing
     representing the same commercial offer"


It does NOT mean:

- same Property;
- same source identity;
- superseded Listing;
- previous version;
- price-history predecessor;
- raw snapshot lineage.


==================================================
10. CANONICAL LISTING RULE
==================================================

Define the canonical relationship:

Canonical Listing:
    duplicate_of_id IS NULL


Duplicate Listing:
    duplicate_of_id points directly to a canonical Listing.


Preferred invariant for MVP:

Do NOT create duplicate chains.


Invalid conceptual structure:

A -> B -> C


Preferred:

B -> A
C -> A


where A is canonical.


Document this as a future persistence/dedup guardrail.


Do NOT implement validation or migration in this task.


==================================================
11. SAME-SOURCE DUPLICATE VS CROSS-SOURCE DUPLICATE
==================================================

Explicitly distinguish:

Same source + same external_id:
    SAME LISTING
    → reuse Listing row

Different source and/or different external_id but heuristic says same offer:
    DIFFERENT LISTING ROWS
    → may later relate through duplicate_of_id


This distinction is critical.


==================================================
12. MULTIPLE LISTINGS FOR ONE PROPERTY
==================================================

The contract must explicitly allow:

Property A
    ├── Listing source X / external 100
    ├── Listing source X / external 200
    └── Listing source Y / external ABC


These are three Listing identities.


They may represent:

- different brokers;
- owner vs broker;
- repost;
- distinct commercial offers;
- duplicate advertisements.


Do not merge solely because property_id matches.

16. PROPERTY REASSIGNMENT DECISION
==================================================

Define what happens if the same hard Listing identity:

source_id + external_id

later resolves to another Property.


Do NOT silently choose without discussion.


Preferred MVP contract:

Treat this as a data-consistency conflict.

Do NOT silently reassign property_id during ordinary persistence.


Reason:

Hard source identity should not unexpectedly migrate between physical units.


Future handling may include:

- review;
- rematching workflow;
- explicit reassignment service.


For Task #5.18, recommend:

existing Listing + different property_id
    → fail closed with ValueError


Document this recommendation.


==================================================
17. SOURCE REASSIGNMENT
==================================================

Existing Listing source_id must never be changed during normal persistence.

A Listing identity cannot migrate from one Source namespace to another.


==================================================
18. EXTERNAL ID REASSIGNMENT
==================================================

Existing Listing external_id must never be changed during normal persistence.

Changing external_id means a different source identity.


==================================================
19. DUPLICATE REASSIGNMENT
==================================================

Do NOT let ordinary ListingPersistenceService decide duplicate_of_id.


duplicate_of_id must be owned by a later dedicated cross-source
deduplication/classification service.


Therefore Task #5.18 should:

- create Listing with duplicate_of_id=None;
- preserve existing duplicate_of_id when reusing a Listing;
- never clear or rewrite duplicate_of_id as side effect of normal persistence.


Document this as required future behavior.
