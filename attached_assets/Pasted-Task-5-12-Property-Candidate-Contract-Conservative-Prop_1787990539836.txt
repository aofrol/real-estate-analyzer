Task #5.12 — Property Candidate Contract + Conservative Property Matcher

Goal:
Introduce a framework-independent PropertyCandidate contract,
PropertyCandidateProvider interface, and the first conservative deterministic
Property matcher for already-resolved Buildings.

The matcher must prefer ambiguity over unsafe forced matching.

IMPORTANT DOMAIN CONSTRAINT

Current Property data does NOT contain a truly stable cross-source apartment
identity such as:

- apartment number;
- cadastral number;
- canonical external property ID.

Therefore:

floor + rooms + is_studio + area

must be treated as a descriptive signature only.

It may support a conservative MVP heuristic match, but it must NOT be treated
as guaranteed physical-apartment identity.

according to the exact area normalization rule below.


==================================================
10. AREA NORMALIZATION RULE
==================================================

Do NOT compare raw floats directly.

Use:

Decimal
ROUND_HALF_UP


Normalize both areas by converting through string representation:

Decimal(str(value))


Then quantize both to:

Decimal("0.01")


with:

ROUND_HALF_UP


Conceptually:

Decimal(str(value)).quantize(
    Decimal("0.01"),
    rounding=ROUND_HALF_UP,
)


Examples:

55.5
55.50

must compare equal.


55.504

normalizes to:

55.50


55.505

normalizes to:

55.51


Do NOT use:

- float epsilon;
- abs(a - b);
- percentage tolerance;
- configurable area tolerance.

This task must stay deterministic.


==================================================
11. MATCHING BEHAVIOR
==================================================

CASE A — provider returns no candidates

Return:

PropertyMatchResult(
    matched=False,
    candidate_key=None,
    confidence=0.0,
    reason="no_property_candidates",
)


CASE B — candidates exist but none match exact descriptive signature

Return:

PropertyMatchResult(
    matched=False,
    candidate_key=None,
    confidence=0.0,
    reason="no_exact_property_signature",
)


CASE C — exactly one candidate matches exact descriptive signature

Return:

PropertyMatchResult(
    matched=True,
    candidate_key=<matching candidate key>,
    confidence=0.80,
    reason="exact_descriptive_signature",
)


IMPORTANT:

confidence=0.80 is an internal heuristic confidence score.

It is NOT:

- a statistical probability;
- proof that both source listings represent the same physical apartment.


CASE D — two or more candidates match exact descriptive signature

Return:

PropertyMatchResult(
    matched=False,
    candidate_key=None,
    confidence=0.0,
    reason="ambiguous_property_candidates",
)


This is a hard safety behavior.

Do NOT choose one candidate using:

- list order;
- key sorting;
- UUID;
- creation time;
- source;
- price;
- external_id;
- first result;
- last result.


==================================================
12. CONSERVATIVE MATCHER DOCSTRING
==================================================

Document clearly in ConservativePropertyMatcher:

A unique exact descriptive signature is accepted only as an MVP heuristic
match within one already-resolved Building.

It is not guaranteed physical-apartment identity.

If more than one candidate shares the same signature, the result must be
ambiguous.

Future identity strengthening may use:

- apartment number;
- cadastral identifier;
- source crosswalk;
- richer canonical property identity data.

rooms=None


Do not solve persistence compatibility here.
