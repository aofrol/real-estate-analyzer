==================================================
3. BUILDING MATCH RESULT
==================================================

In:

backend/app/matching/building.py

define:

BuildingMatchResult

Use:

@dataclass(frozen=True, slots=True)

from Python standard library dataclasses.


The result must contain:

matched: bool

candidate_key: str | None

confidence: float

reason: str


Semantics:

matched
    Whether the matcher considers an existing building candidate to be a
    sufficiently strong match.

candidate_key
    Framework-independent identifier of the matched candidate supplied by a
    future candidate provider.

    It is NOT necessarily a database UUID.

    Examples in future implementations might include:
    - a stringified UUID;
    - an external candidate key;
    - another application-level identifier.

    For an unmatched result it must be None.

confidence
    Deterministic matching confidence in the inclusive range 0.0–1.0.

    This is a matcher score, NOT a statistical probability.

reason
    Short machine-readable diagnostic reason.

    Example future values:
    - "exact_address"
    - "coordinates"
    - "address_and_coordinates"
    - "no_candidates"

Do NOT create an enum yet.
Keep reason as str for this MVP contract.


==================================================
4. RESULT INVARIANTS
==================================================

BuildingMatchResult must validate its own structural invariants in
__post_init__.

Required invariants:

1. confidence must be between 0.0 and 1.0 inclusive;

2. if matched is True:
   candidate_key must be a non-empty string;

3. if matched is False:
   candidate_key must be None;

4. reason must be a non-empty string.

Raise ValueError with concise messages when an invariant is violated.

Do NOT implement any actual building matching logic in __post_init__.


==================================================
5. BUILDING MATCHER ABSTRACT INTERFACE
==================================================

In the same module define:

class BuildingMatcher(ABC)

with exactly one abstract operation:

match(listing: NormalizedListing) -> BuildingMatchResult


Requirements:

- inherit from ABC;
- use @abstractmethod;
- accept NormalizedListing;
- return BuildingMatchResult;
- contain no implementation logic;
- contain no database access;
- contain no ORM dependencies.


Architectural meaning:

NormalizedListing
        ↓
BuildingMatcher
        ↓
BuildingMatchResult


==================================================
6. IMPORTANT RESPONSIBILITY BOUNDARY
==================================================

Document clearly:

BuildingMatcher IS responsible for deciding whether a normalized listing
matches a known building candidate according to a matching strategy.

Future strategies may use:

- normalized address;
- city;
- latitude;
- longitude;
- building type;
- other deterministic building-level attributes.


BuildingMatcher IS NOT responsible for:

- collecting listings;
- normalization;
- geocoding;
- creating Building records;
- updating Building records;
- database transaction management;
- Property matching;
- Listing persistence;
- duplicate listing detection;
- comparable selection;
- valuation.
