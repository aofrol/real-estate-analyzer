Task #5.21 — End-to-End Listing Processing Pipeline

Goal

Assemble the already implemented ingestion / normalization / building / property / listing / price-history components into one application-level processing pipeline for a single source listing observation.

This task must prove that one raw source observation can move through the complete backend persistence flow, and that a repeated observation of the same source listing reuses the same entities and records price history correctly.

IMPORTANT:
- This is application orchestration only.
- Do not redesign existing services.
- Do not implement Celery scheduling.
- Do not implement cross-source deduplication.
- Do not implement frontend/API endpoints.
- Do not change database schema or Alembic migrations.
- Do not commit automatically.
- Inspect the current repository first and adapt exact imports/signatures to the code that actually exists.

--------------------------------------------------

We want one application service that coordinates a single normalized listing observation through:

External observation
    ↓
Normalization
    ↓
Building resolution
    ↓
Building persistence
    ↓
Property resolution
    ↓
Property persistence
    ↓
Listing current-state persistence
    ↓
Listing price-history persistence

Target conceptual flow:

source_id + persisted RawListing
        ↓
NormalizationService
        ↓
BuildingCandidateProvider
        ↓
BuildingMatcher
        ↓
BuildingResolutionService
        ↓
BuildingPersistenceService
        ↓
PropertyCandidateProvider
        ↓
PropertyMatcher
        ↓
PropertyResolutionService
        ↓
PropertyPersistenceService
        ↓
ListingPersistenceOrchestrator
        ↓
Listing + optional ListingPriceHistory

The caller owns the SQLAlchemy Session and enclosing transaction.

The new pipeline service MUST NOT call:
- commit()
- rollback()
- close()

--------------------------------------------------
3. Scope clarification: raw ingestion
--------------------------------------------------

Do NOT redesign RawListing persistence in this task.

The current schema has:

UNIQUE(source_id, external_id)

Therefore RawListing currently behaves as one persisted raw source record per source listing identity, not a true append-only observation journal.

For Task #5.21, the processing pipeline should accept an already persisted RawListing or otherwise reuse the current ingestion boundary exactly as the repository currently supports it.

Do not introduce a second raw-observation history table.
Do not remove the existing uniqueness constraint.
Do not change migrations.

If repeated source observation cannot create another RawListing because of the current unique constraint, test repeated processing using the same persisted RawListing with updated/raw fixture input through the narrowest existing supported boundary.

Document this limitation explicitly.

7. Exact processing semantics
--------------------------------------------------

For one source observation:

STEP A — Normalize

Normalize using:
- authoritative persisted external_id;
- raw_data copy;
- existing NormalizationService;
- existing canonical NormalizedListing contract.

Do not mutate raw input.

STEP B — Building

Use existing building candidate/match/resolution logic.

Expected semantics:
- one exact match → reuse existing Building;
- no match → create Building;
- ambiguous → fail closed;
- no silent arbitrary candidate selection.

Persist using BuildingPersistenceService.

STEP C — Property

Use existing property candidate/match/resolution logic scoped to resolved Building.

Expected semantics:
- one exact descriptive-signature match → reuse Property;
- no match → create Property;
- ambiguous → fail closed.

Persist using PropertyPersistenceService.

STEP D — Listing

Call existing ListingPersistenceOrchestrator using:
- authoritative Source identity;
- resolved Property identity;
- NormalizedListing.

Do not duplicate ListingPersistenceService logic inside the new pipeline.

Do not duplicate ListingPriceHistoryService logic inside the new pipeline.

The existing ListingPersistenceOrchestrator remains responsible for:
- capturing previous price before current Listing mutation;
- persisting current Listing state;
- invoking price-history persistence when appropriate.

STEP E — Return result

Return resolved/persisted:
- normalized listing;
- Building;
- Property;
- Listing;
- optional ListingPriceHistory.

--------------------------------------------------
8. Critical identity behavior
--------------------------------------------------

The integration tests must prove all of the following.

FIRST OBSERVATION

Given one Mock source listing:

- Building is created.
- Property is created.
- Listing is created.
- Listing identity is source_id + external_id.
- Listing.duplicate_of_id is NULL.
- no ListingPriceHistory row is created for initial Listing creation.

SECOND OBSERVATION — SAME IDENTITY / SAME PRICE

Process the same source + external_id again with the same canonical apartment identity and same price.

Must prove:

- same Building row reused;
- same Property row reused;
- same Listing row reused;
- no second Listing created;
- no price history created;
- no property reassignment;
- no duplicate_of_id mutation.

THIRD OBSERVATION — SAME IDENTITY / CHANGED PRICE

Process same source + external_id again, same apartment, but changed asking price.

Must prove:

- same Building reused;
- same Property reused;
- same Listing reused;
- Listing current asking_price becomes new price;
- Listing current asking_price_per_sqm becomes the new canonical value;
- exactly one ListingPriceHistory row is created;
- history row points to same Listing;
- history row contains the NEW observed price;
- no history row is created with old price;
- stable Listing.id remains unchanged.

OPTIONAL FOURTH OBSERVATION

If straightforward, process changed URL with same identity:

- Listing identity remains unchanged;
- non-null incoming URL updates current URL;
- incoming None does not erase existing URL.

Do not expand scope if this requires unrelated changes.
