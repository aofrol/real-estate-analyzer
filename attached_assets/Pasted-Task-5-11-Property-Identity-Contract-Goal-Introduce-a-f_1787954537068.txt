Task #5.11 — Property Identity Contract

Goal:
Introduce a framework-independent contract for identifying whether a
NormalizedListing refers to an existing Property inside a known Building.

This task defines identity semantics only.

Do NOT query PostgreSQL.
Do NOT use SQLAlchemy.
Do NOT create Property ORM rows.
Do NOT persist Listings.
Do NOT implement fuzzy identity logic yet.


CURRENT DOMAIN FLOW

NormalizedListing
        ↓
Building resolved / persisted
        ↓
building_key
        ↓
Property identity decision
        ↓
PropertyMatchResult

==================================================
2. IMPORTANT IDENTITY PRINCIPLE
==================================================

For Task #5.11 do NOT claim that area + rooms + floor uniquely identify a
physical apartment.

These attributes may be useful for candidate similarity, but are not a safe
global identity key.

The contract must distinguish:

A. confidently matched existing Property;
B. no safe match;
C. ambiguous possible matches.


==================================================
3. CREATE PACKAGE FILE
==================================================

Create:

backend/app/matching/property.py


Define:

@dataclass(frozen=True, slots=True)
class PropertyMatchResult


Fields:

matched: bool

candidate_key: str | None

confidence: float

reason: str


Use semantics consistent with BuildingMatchResult, but keep Property as a
separate contract.


==================================================
4. PROPERTY MATCH RESULT INVARIANTS
==================================================

Validate in __post_init__:

1. confidence must be numeric, finite, and between 0.0 and 1.0 inclusive;

2. matched=True requires candidate_key to be a non-empty string;

3. matched=False requires candidate_key is None;

4. reason must be a non-empty string.

Raise ValueError containing the relevant field name.


==================================================
5. PROPERTY MATCHER CONTRACT
==================================================

In the same file define:

class PropertyMatcher(ABC)


Method:

@abstractmethod
def match(
    self,
    *,
    listing: NormalizedListing,
    building_key: str,
) -> PropertyMatchResult:
    ...


The matcher receives:

listing
    normalized source listing data

building_key
    already resolved persisted Building identity


==================================================
6. BUILDING KEY VALIDATION BOUNDARY
==================================================

The abstract PropertyMatcher contract itself must NOT parse UUIDs.

building_key is framework-independent string identity.

Concrete SQLAlchemy implementations may later interpret it as UUID.

Do not couple this contract to database types.


==================================================
7. PROPERTY MATCHER RESPONSIBILITY
==================================================

PropertyMatcher is responsible only for deciding whether a listing corresponds
to a known Property candidate within the already-resolved Building.

It is NOT responsible for:

- building matching;
- building persistence;
- loading ORM models;
- creating Property;
- updating Property;
- creating Listing;
- source ingestion;
- normalization;
- deduplication;
- valuation.

8. IDENTITY SIGNALS
==================================================

Document which signals are potentially useful.

Expected examples may include:

- area_sqm.

But do NOT assume all of them exist until inspection confirms it.


==================================================
9. IDENTITY SAFETY RULE
==================================================

Explicitly document in PropertyMatcher docstring:

For current MVP data, apartment attributes such as:

- floor;
- rooms;
- studio status;
- area

are descriptive attributes and may help compare candidates, but they are not
guaranteed unique identifiers of a physical apartment.

Therefore a future matcher must be allowed to return ambiguous rather than
forcing a match.
