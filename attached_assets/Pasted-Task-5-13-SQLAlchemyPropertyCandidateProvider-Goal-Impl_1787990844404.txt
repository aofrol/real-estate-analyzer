Task #5.13 — SQLAlchemyPropertyCandidateProvider

Goal:
Implement a SQLAlchemy-backed PropertyCandidateProvider that loads Property
rows for one already-resolved Building and maps them into framework-independent
PropertyCandidate objects.

This task connects the clean property-matching layer to the ORM persistence
layer.

Do NOT perform matching here.
Do NOT create or update Property rows.
Do NOT persist Listing rows.
Do NOT commit or rollback transactions.

NormalizedListing
        +
building_key
        ↓
SQLAlchemyPropertyCandidateProvider
        ↓
PropertyCandidate[]
        ↓

        ↓

==================================================
3. RESPONSIBILITY BOUNDARY
==================================================

SQLAlchemyPropertyCandidateProvider is responsible only for:

1. validating/parsing building_key;
2. querying Property rows for that Building;
3. mapping ORM rows into PropertyCandidate values.

It must NOT:

- decide which candidate matches;
- calculate confidence;
- resolve ambiguity;
- create Property;
- update Property;
- delete Property;
- create Listing;
- persist Listing;
- commit;
- rollback;
- flush;
- normalize source data;
- perform valuation.


==================================================
4. BUILDING KEY VALIDATION
==================================================

building_key comes from the application layer as a framework-independent string.

Inside this concrete SQLAlchemy provider:

1. require building_key to be a non-empty string;
2. parse it using Python UUID;
3. on invalid value raise ValueError containing:

building_key


Example:

try:
    building_id = UUID(building_key)
except (AttributeError, TypeError, ValueError):
    raise ValueError("building_key must be a valid UUID") from None


Do NOT query if building_key is invalid.


==================================================
5. QUERY SCOPE
==================================================

Query Property rows with:

Property.building_id == building_id


Do NOT filter by:

- floor;
- rooms;
- is_studio;
- area_total;
- external listing ID;
- source;
- price.


This is intentional.

The provider supplies candidates.

ConservativePropertyMatcher decides whether any candidate matches the
descriptive signature.


==================================================
6. WHY NOT PRE-FILTER
==================================================

Document this in the provider docstring or module comments:

The provider loads all Property candidates within the resolved Building.

It intentionally does not pre-filter by floor/rooms/studio/area because:

1. matching responsibility belongs to ConservativePropertyMatcher;
2. the matcher must be able to distinguish:
   - no_property_candidates;
   - no_exact_property_signature;
   - ambiguous_property_candidates;
3. pre-filtering here would leak identity logic into the SQLAlchemy boundary.


==================================================
7. DETERMINISTIC ORDER
==================================================

The query must use deterministic ordering:

.order_by(Property.id.asc())


Candidate order must NOT be used by the matcher to resolve ambiguity.

Ordering is only for deterministic behavior/tests/debugging.


==================================================
8. QUERY SHAPE
==================================================

Prefer the same SQLAlchemy 2.x style already used in the project.

Expected shape:

statement = (
    select(Property)
    .where(Property.building_id == building_id)
    .order_by(Property.id.asc())
)

properties = self._session.scalars(statement).all()


Do not use legacy:

session.query(...)


==================================================
9. PROPERTY → PROPERTYCANDIDATE MAPPING
==================================================

For each Property row return:

PropertyCandidate(
    key=str(property.id),
    floor=property.floor,
    rooms=property.rooms,
    is_studio=property.is_studio,
    area_sqm=float(property.area_total),
)


IMPORTANT:

Property.area_total is Numeric/Decimal at the ORM boundary.

Convert to float only when constructing PropertyCandidate.

Do not change PropertyCandidate to Decimal in this task.


==================================================
10. AREA CONVERSION RULE
==================================================

Use:

float(property.area_total)


Do NOT:

- quantize here;
- round here;
- format as string;
- apply tolerance here.


Area comparison/quantization remains owned by:

ConservativePropertyMatcher


The ORM provider only performs representation conversion.


==================================================
11. STUDIO ROOMS MISMATCH
==================================================

Current known contract:

    int | None

    NOT NULL

    rooms=None


This mismatch is NOT solved in Task #5.13.

Provider behavior:

return the actual ORM value:

rooms=property.rooms


Do NOT convert:

0 -> None
1 -> None
None -> 0
None -> 1


Do not introduce special studio logic.

Explicitly report this mismatch again as a blocker before Property persistence.


==================================================
12. LISTING PARAMETER
==================================================

The provider signature includes:

listing: NormalizedListing

because it conforms to PropertyCandidateProvider.

However, the SQLAlchemy provider must NOT use listing fields to narrow the SQL
query in this task.

Do not mutate listing.

Do not copy listing.

It is acceptable for listing to be unused after interface conformance.


==================================================
13. BUILDING EXISTENCE
==================================================

Do NOT separately query Building.

If:

is syntactically valid UUID but no Property rows exist for that building_id,

Do not distinguish:

- Building UUID does not exist.

That distinction is outside this provider's responsibility.

The already-resolved Building flow is expected to provide a valid building_key.
